# Accessibility: Evidence, Impact, and Risks

Read when drafting or revising the accessibility block. Follow the block approval cycle in `SKILL.md` and the shared findings rules. Write the resulting specification in Russian.

## Find applicable expert guidance

Consult current sources for the component's actual interaction and platform. Use WCAG and WAI-ARIA specifications for normative accessibility requirements, WAI-ARIA Authoring Practices for interaction patterns, and relevant official platform guidance or original UX research for usability recommendations. Prefer primary sources; link the exact page supporting each substantive claim. An example pattern is guidance, not proof that a particular implementation is accessible. If sources disagree or do not cover the scenario, say so instead of inventing a universal rule.

## Explain the user effect

In the Codex draft, present each substantive recommendation as **practice → user problem it addresses → expected effect → source**. Explain concretely who benefits and how the practice changes the task: for example, orientation, comprehension, error prevention, keyboard operation, screen-reader feedback, or touch use. In the Figma block, keep those explanations concise and preserve source attribution through nearby links or a compact source list. Do not promise a measured improvement without evidence. Separate a standard's requirement, an expert recommendation, a product decision, an observed design fact, and a result actually tested.

## Surface debatable choices

When more than one credible pattern fits, compare the relevant alternatives before recommending one. Explain why the proposed or user-selected option fits this component, what could go wrong for users, which users or situations are most affected, and how the risk can be reduced or tested. If the choice depends on unknown product behavior, ask one clarification question at a time before describing it as confirmed. Put material unresolved choices and retained risks in the block's bottom «Замечания и спорные моменты» subsection. Do not present a risk-bearing option as WCAG-compliant solely because it appears in a design file or an expert example.
